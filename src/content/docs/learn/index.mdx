Playbooks explain how to frame work before an employee acts. Recipes follow one path from a request to a reviewed result. They used to be a separate Learn portal. They now sit in Resources, beside the product guides that use the same words.

## Start with the decision you need

- [Requirements writing](/learn/requirements-writing/) — describe the outcome and the acceptance criteria a person can check.
- [Blueprints and work orders](/learn/blueprints-work-orders/) — separate a design note from an execution task. The platform does not provide a Blueprint module.
- [Feedback and review](/learn/feedback-review/) — decide whether a finding is a defect, new scope, or a question.
- [Issue to pull request](/recipes/issue-to-pr/) — carry one engineering request through confirmation, execution, verification, and review.
- [Best practices](/resources/best-practices/) — the short rules that show up across those guides.

## Hand the work to the product

A playbook does not create an employee or a pipeline. When the requirement is clear, use [AI employees](/user-guide/ai-employees/) to assign it, or [Software Factory](/software-factory/overview/) when the outcome is a code change. Builders who need a new role continue in [employee definition](/build/employee-definition/).

Before confirming a task, the team should be able to name the outcome, the allowed scope, the observable acceptance check, and where a person must decide. If an answer is missing, ask for that answer. If the answer changes the scope, update the requirement before execution continues.
