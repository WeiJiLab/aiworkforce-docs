Turn a known engineering procedure into a reusable employee capability, then run it through one automation. Use this track when the required role or method is not ready yet. If the board already has suitable employees, start with [Quickstart](/getting-started/quickstart/).

## The example we will build

Continue the form-validation example from [Foundations](/learn/software-factory-foundations/). The team wants a worker that investigates similar requests and prepares a reviewable proposal. Its inputs are the Issue, relevant project materials, and acceptance criteria. Its output must explain the affected behavior and the evidence still needed. Implementation starts only after the request is confirmed on a delivery card.

## Build in this order

| Stage                          | Result to check                                                                        | Authoritative guide                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Define the responsibility      | Required inputs, expected output, exclusions, and acceptance criteria are written down | [Employee definition](/build/employee-definition/)                                                        |
| Prepare access                 | The worker can use the intended repository and tools within its grants                 | [Code repositories](/integrations/code-repositories/) and [employee tools](/integrations/employee-tools/) |
| Try real requests              | A normal request, missing input, and out-of-scope work produce acceptable behavior     | [Employee testing](/build/testing/)                                                                       |
| Publish and create an instance | A published template version is available, and the workspace employee is ready         | [Publishing](/build/publishing/) and [create an employee](/getting-started/first-employee/)               |
| Run once, then automate        | One manual Job run has an inspected result before an automatic trigger is enabled      | [Your first workflow](/getting-started/first-automation/)                                                 |

Record the inputs, accepted outputs, and failures from trials. Package validation checks structure; task trials check behavior. These steps do not require or imply an automatic benchmark service. Publishing a template and enabling a Job are separate actions, and existing employees need an explicit version-adoption plan.

## Completion check

You have identified the template version, a ready workspace employee, recorded task trials, and one inspected manual run. You know which trigger will start later runs and which decisions remain with people. To carry confirmed changes through a team board, continue with [Run a Software Factory](/learn/run-software-factory/).
