Asking an employee for a new prompt at every handoff leaves people coordinating the software lifecycle. Software Factory connects the delivery board's lanes into four loops, so a confirmed card moves through implementation, verification, and release without a fresh prompt in every column. People stay on the judgment calls: scope, the review of evidence, and whether the change ships.

The product surface is the **delivery workbench**. A published board template is the source of the board stages and their automation. Open **Workbench** (工作台) in the primary navigation. The address is `/automations?tab=board-flow`. It uses the same workflow, automation, employees, and evidence as the [Kanban workbench](/workflows/kanban-workbench/) and [issue automation](/workflows/issue-automation/).

## The full flow

Lane employees carry a requirement to a reviewed change. A connected pipeline deploys the merged revision. During operations, a collection job can send incidents and user feedback to the inbox. A person confirms which follow-up becomes the next delivery card (ticket).

<SoftwareFactoryLoop locale="en" />

A **card** is the work item these loops hand off. An imported GitHub, GitLab, Yunxiao, Jira, or Linear issue becomes that card when you route it to a project and confirm it. The card keeps the confirmed scope, the session, the code reference, the test record, and the human decision.

## Choose a collaboration template

The published collaboration template is the primary entry point for Software Factory. It supplies the executable stages behind a board, assigns each stage a task and employee requirement, and names the artifact that must be handed to the next stage. Choose the scenario first, then use the matching path guide to configure and run it. See [Collaboration templates](/software-factory/templates/) for the complete catalog.

## Four template-led paths

| Loop                 | What moves forward                                                                                 | Guide                                                             | Matching template scenarios                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Requirements → card  | A feature brief becomes a reviewed scope and a confirmed card.                                     | [Requirements to a card](/software-factory/requirements-to-card/) | `spec-intake-to-rfc-ticket-breakdown`                                                         |
| Card → pull request  | A confirmed card becomes an implemented change with a pull request, branch, or commit on the card. | [Card to a pull request](/software-factory/card-to-pr/)           | `pr-author`                                                                                   |
| Pull request → merge | A reviewed change is repaired, verified, and presented for a person's merge and release decision.  | [Pull request to merge](/software-factory/pr-to-merge/)           | `pr-spec-adherence-check`, `release-candidate-readiness-review`                               |
| Signal → card        | Feedback or an incident is investigated, and a person decides which follow-up becomes a card.      | [Signal to a card](/software-factory/signal-to-card/)             | `customer-escalation-to-product-fix`, `incident-investigator`, `docs-gap-from-support-ticket` |

The four paths are views into the collaboration template catalog. The selected template and its published version determine the executable stages and their handoff contracts.

## How the loops sit on the board

Built-in lanes, in order:

```text
Requirements (需求) → Development (开发) → Test deployment (测试发布) → Testing (测试验证) → Production (生产发布) → Done (已完成)
```

| Loop                 | What carries it on the board                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Requirements → card  | The Requirements lane. A person confirms scope, acceptance criteria, and the repositories the change may touch.                                     |
| Card → pull request  | The Development lane. The lane employee works in a session and records a pull request, branch, or commit.                                           |
| Pull request → merge | Test deployment (测试发布), Testing (测试验证), and Production (生产发布). Merge and production run when the repository and pipeline are connected. |
| Signal → card        | The inbox and a collection Job. A confirmed follow-up enters Requirements.                                                                          |

A step inside a lane is execution state. Custom boards can arrange lanes differently. There is no WIP limit. Cards that will be tested together can share a batch. The Done lane closes out delivery resources. Operations continues after release, and production signals can start the next card.

## People keep the decisions

Confirming a draft lets the development lane proceed. That confirmation leaves repository credentials and pipeline setup where they already are: on the workspace and the project. During a run, answer questions on the card. Taking over stops automatic progress and keeps the current state. Hand the work back explicitly. Resuming a pause leaves a takeover in place. An operation on a shared batch can affect every member card.

The records around a decision are [evidence](/software-factory/evidence/), [quality gates](/software-factory/quality-gates/), and [release governance](/software-factory/release-governance/).
