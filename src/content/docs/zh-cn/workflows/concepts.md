AI Workforce 是以工作流为中心的平台。**工作流**是可复用的工作定义。**自动化**是启动并持续推动这项工作的机制。**智能体**在产品里是数字员工，负责执行具体步骤。**运行**是一次执行实例。**任务**是这次执行中的一个工作单元。

这些词不是三个产品模块，也不是三套引擎。软件工厂、交付看板和 Issue 处理，都是同一套工作流的应用。

创建智能体，得到的是一个可以被调用的执行者。创建工作流，得到的是可以继续下去的工作：触发、定义、执行者、记录，以及人可以核对的证据。智能体是工作流调用的执行资源。

## 在产品里打开哪里

文档使用上面的词。界面使用这些名称：

| 概念   | 产品对象                                               |
| ------ | ------------------------------------------------------ |
| 工作流 | 交付看板、泳道上的**编排**，或员工技能里声明的工作流   |
| 自动化 | 一个自动化 **Job**：任务、执行者，以及调用它的触发规则 |
| 智能体 | 数字员工，或看板上的代码执行器                         |
| 运行   | 一次 Job 运行，或一次记下每个节点运行的编排运行        |
| 任务   | 收件箱事项、交付卡片，或编排中的一个节点               |
| 证据   | 与这项工作放在一起的会话、代码引用、测试记录和人工决定 |

在 `/automations` 打开**自动化**管理 Job。在同一页打开**编排**管理泳道编排。在 `/automations?tab=board-flow` 打开交付工作台。

## 生命周期

```text
触发 → 上下文 → 定义 → 智能体执行 → 环境
     → 验证 → 证据 → 交付 → 反馈
```

| 阶段       | 它回答什么               | 本版本                                                                           |
| ---------- | ------------------------ | -------------------------------------------------------------------------------- |
| 触发       | 什么启动工作？           | 手动运行、日程、Webhook、GitHub 事件轮询、Issue、IM 消息或看板泳道。限制见下文。 |
| 上下文     | 执行者可以读什么？       | 工作空间、仓库连接、事项或卡片、会话记忆和员工知识。                             |
| 工作流定义 | 步骤和依赖是什么？       | 一个 Job、由执行器组成的泳道编排，或技能工作流。没有脱离看板的通用流程画布。     |
| 智能体执行 | 谁执行这一步？           | Job 的员工、泳道员工，或允许列表中的看板代码执行器。                             |
| 执行环境   | 在哪里运行？             | 平台运行时、自托管部署或已授权设备。没有按卡片准备的沙箱。                       |
| 验证       | 工作是否达到约定结果？   | 看板上的测试、验收标准，以及人工比较。没有自动的业务分数。                       |
| 证据与产物 | 用什么证明，产出了什么？ | 会话、文件、代码引用或 Pull Request、测试记录，以及卡片上的决定。                |
| 交付       | 结果送到哪里？           | 收件箱更新、Pull Request、审阅、发布泳道或一条消息。发布仍然要求集成已经存在。   |
| 反馈与恢复 | 人或失败介入后怎么办？   | 人工确认、接管、交还、编排节点重试，以及下一次运行。                             |

触发并不定义工作。发布 Job 或启用编排不会创建运行。一次成功的运行本身也不等于业务请求已经解决。

## 可以复用的部分

| 部分     | 作用                                                                            |
| -------- | ------------------------------------------------------------------------------- |
| 触发     | 何时调用这份定义。Job 和编排各自保存触发规则。                                  |
| 上下文   | 工作空间、输入，以及不可信的事件载荷。事件不会把 Token 和工具授权注入执行配置。 |
| 执行     | 员工会话或代码执行器。                                                          |
| 控制     | 编排连线条件、节点的 `when` 条件、重试、上游失败策略和人工确认。                |
| 环境     | 运行前已经配置的运行时位置、设备、仓库和流水线资源。                            |
| 验证     | 测试泳道、验收标准和审阅。它不同于员工包评测。                                  |
| 输出     | 产物、收件箱事项、卡片更新和 Pull Request。                                     |
| 可观测性 | 运行历史、会话、节点状态，以及模型渠道上的成本。本版本不包括第二套追踪产品。    |

## 三种运行方式

记录是同一套。差别在于下一次运行由什么引起。

```text
一次性       在 Job 上手动运行，然后结束
事件驱动     外部事件入场，产生一次运行
持续运行     交付看板持续消耗卡片
```

| 方式     | 何时开始                                           | 何时结束                     | 产品界面                         |
| -------- | -------------------------------------------------- | ---------------------------- | -------------------------------- |
| 一次性   | 你选择**手动运行**                                 | 该运行进入终态               | 一个自动化 Job                   |
| 事件驱动 | 日程到达、Webhook 进入，或轮询到的 GitHub 事件匹配 | 这一次调用的运行结束         | Job 的触发规则，或编排的定时触发 |
| 持续运行 | 卡片在泳道上就绪，或泳道扫描发现工作               | 卡片进入已完成，或人把它停下 | 交付工作台和泳道编排             |

保存、发布和启用是不同的动作。已暂停的 Job 仍可手动运行。这次手动运行不会重新打开自动触发。只有一个执行器时，应保留为 Job：编排至少要有两个执行器才能启用。

## 交付看板就是这里的看板

本产品里的看板是交付工作台，不是软件工厂旁边的另一块看板。看板是工作管理界面。工作流是泳道规则。自动化启动并继续泳道工作。员工负责执行。运行是记录。证据是审阅者用来接受卡片的依据。

内置泳道按交付顺序是：

```text
需求 → 开发 → 测试发布 → 测试验证 → 生产发布 → 已完成
DRAFT   DEV     PREPARE     TEST         RELEASE      DONE
```

卡片上的步骤是执行状态：澄清、就绪、编码、运行中、通过、失败、合并、部署、核对，或等待人。不要把列当成手工维护的标签。可以添加自定义泳道。自定义泳道的行为来自看板模板，不继承内置种类。

没有在制品上限。并行指多张卡片，以及在测试发布、测试验证、生产发布和已完成中把卡片组成批次。对批次的操作可能影响其中每张卡片。

**分派**把已确认的卡片交给泳道上配置的员工。**编排**是工作台沿这些泳道推进卡片和批次，包括把执行器串起来的泳道编排。分派不选择模型，也不跳过验证。编排不是通用的多 Agent 运行时。阅读[任务分派](/zh-cn/software-factory/dispatch/)和 [Agent 编排](/zh-cn/software-factory/orchestration/)。

## 验证不是员工评测

工作流验证问的是这次运行有没有达到验收标准：测试、记录下来的比较和人工决定。员工评测问的是员工包或插件是否按定义工作。一段流畅的会话两者都不是。见[业务验证](/zh-cn/software-factory/business-verification/)和[执行评测](/zh-cn/software-factory/evaluation/)。

## 示例 A. GitHub Issue

| 部分   | 本版本                                                              | 本版本没有                             |
| ------ | ------------------------------------------------------------------- | -------------------------------------- |
| 触发   | 通过 GitHub Token 轮询观察到 Issue 打开、关闭、重新打开、标签或评论 | GitHub App、仓库 Webhook 或即时投递    |
| 上下文 | 白名单事件字段、工作空间和仓库连接                                  | 检出事件 SHA；事件本身不能证明已经检出 |
| 智能体 | Job 的执行员工                                                      | 自动选择负责人                         |
| 步骤   | Job 运行。它可以收集收件箱事项。改代码之前由人确认范围。            | 内置分类器、重复检测或优先级模型       |
| 验证   | 你检查这次运行。只有事项成为已确认卡片之后，才进入交付验证。        | 自动把 GitHub Issue 标为已解决         |
| 输出   | 一次运行、可选的收件箱事项，以及看板执行卡片后的 Pull Request       | 事件适配器把结果写回 GitHub            |
| 人     | 确认草稿。在卡片上回答问题。                                        | 无人值守的实现                         |

第一次成功的轮询只建立基线。之后的间隔至少 60 秒，观察到的是状态变化，不是完整的 Webhook 流。细节见[事件驱动自动化](/zh-cn/automate/event-driven/)。操作路径见 [Issue 自动化](/zh-cn/workflows/issue-automation/)。

## 示例 B. Pull Request 审阅

| 部分   | 本版本                                                           | 本版本没有                          |
| ------ | ---------------------------------------------------------------- | ----------------------------------- |
| 触发   | PR 打开、更新、可审阅、关闭、合并、重新打开、标签、评论或 Review | Checks 完成，或 Review 讨论串被解决 |
| 上下文 | 事件载荷中的 PR 字段，包括草稿状态和目标分支过滤                 | 分支事件上最后推送者的身份          |
| 智能体 | Job 上的员工                                                     | 代表平台批准的审阅机器人            |
| 步骤   | 员工调查，并把结果留在会话里                                     | 由 Job 自动合并                     |
| 验证   | 你阅读会话。合并和生产留在集成存在时的发布泳道。                 | 代替 GitHub Review                  |
| 输出   | 一次运行，以及员工在授权范围内产出的内容                         | 保证在 GitHub 上留下审阅评论        |
| 人     | 审阅决定，以及发布批准                                           | 用户名白名单和多仓库订阅            |

## 示例 C. 由看板驱动的软件工厂

| 部分   | 本版本                                                                     | 本版本没有                   |
| ------ | -------------------------------------------------------------------------- | ---------------------------- |
| 触发   | 就绪的卡片、泳道扫描或泳道编排触发                                         | 手工挪动状态来假装已经执行   |
| 上下文 | 卡片、项目、允许的仓库和泳道员工                                           | 按卡片准备的沙箱或预览浏览器 |

| 输出   | 会话、代码引用或 Pull Request、测试记录和卡片上的决定                      | 第二套证据产品               |
| 人     | 确认草稿、回答卡片、接管，并决定是否发布                                   | 在制品上限                   |

## 示例 D. 定时调研

| 部分   | 本版本                                 | 本版本没有               |
| ------ | -------------------------------------- | ------------------------ |
| 触发   | Job 上的 Cron，或编排上的 Cron         | 调研 Agent 产品          |
| 上下文 | 任务正文，以及该员工已被允许调用的工具 | 专门的多仓库调研范围     |
| 智能体 | 一名执行员工                           | 自行展开的团队           |
| 步骤   | 运行、产出产物、结束                   | 循环计数器或无终点的监控 |

| 输出   | 会话及其文件                           | 自动发布                 |

## 限制

- Job 没有分支画布。分支、扇出和重试属于泳道编排，而编排是为某个工作空间、看板和泳道创建的。
- 编排编辑器中的触发是手动和 Cron。GitHub、Webhook、Issue 和 IM 触发属于 Job。
- GitHub 事件用 Token 轮询。它们不是 Webhook 流，适配器也不会写回 GitHub。
- 技能工作流可以声明技能、subagent、工具、人工确认、并行、条件和分支。要在运行轨迹里确认。正文里写出步骤名称并不会创建它。
- 人仍然确认范围、接管执行并批准发布。
