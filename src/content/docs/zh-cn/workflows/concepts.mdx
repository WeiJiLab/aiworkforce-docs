工作流是一份可复用的工作约定，描述输入、步骤、预期结果和检查方式。自动化启动这项工作，执行者完成步骤，运行记录一次具体执行。

例如，重复采集 Issue 的任务沿用同一份指令，每次调用检查新的报告；运行记录说明这一次发现了什么。请求转为交付草稿后，仍需由人确认是否开始开发。

## 从工作定义到一次结果

发布或启用定义不会创建运行。依赖自动触发之前，先检查一次实际执行的结果。运行成功后，仍要对照任务要求判断是否达到预期。

## 决定何时启动

- **手动：**在 Job 上选择手动运行，检查这一次执行。
- **定时或事件驱动：**可用的触发规则启动执行。Job 在对应能力可用时支持日程、入站 Webhook、GitHub 事件轮询、Issue 和 IM 触发。编辑器中的泳道编排支持手动和 cron 触发。
- **持续看板工作：**泳道规则和扫描沿交付流程推进就绪卡片，卡片状态反映执行进展。

保存、发布、运行和启用是不同动作。暂停自动执行的已发布 Job 仍可手动运行，但不会因此重新启用自动触发。各动作的具体效果见[自动化概念](/zh-cn/automate/fundamentals/)。

## 准备执行者、上下文和证据

工作空间员工提供岗位和能力，部分看板步骤使用允许列表中的代码执行器。配置的运行时与环境提供执行资源，任务使用连接前还需要执行者授权。事件载荷是任务输入，不能提供凭据或工具授权。

**会话**记录对话和执行上下文，**产物**是输出，**证据**把输出与来源、受测版本、环境和检查联系起来。软件变更的审阅者对照已确认的验收标准判断结果。员工包评测则通过多次试验检查可复用能力，与验证本次交付不同。见[业务验证](/zh-cn/software-factory/business-verification/)和[员工评测](/zh-cn/software-factory/evaluation/)。

## 进入对应指南

- [Issue 自动化](/zh-cn/workflows/issue-automation/)：调查 GitHub Issue 或收件箱事项，开发前确认请求。GitHub 事件通过轮询获得，事件适配器不向 GitHub 写回。[事件驱动自动化](/zh-cn/automate/event-driven/)说明事件源配置。
- [Pull Request 自动化](/zh-cn/workflows/pull-request-automation/)：由员工检查 PR 事件，并查看会话结果。事件适配器不保证生成审阅评论或自动合并。
- [看板工作台](/zh-cn/workflows/kanban-workbench/)：跟踪交付泳道中的卡片和批次。分派把就绪卡片交给泳道员工，编排推进卡片、批次和泳道执行。
- [调研与监控](/zh-cn/workflows/research-monitoring/)：按日程产出材料，或由已配置的监控事件启动。发布或采取行动前由人检查结果。

## 扩大使用前明确边界

Job 没有分支画布。泳道编排支持连线条件、节点条件、重试和上游失败策略，编辑器要求至少两个执行器才能启用。技能工作流可以声明工具、子智能体、审批、并行、条件和分支步骤，但需要所选运行时实际执行并留下追踪记录。具体选择见[自定义工作流](/zh-cn/workflows/custom-workflows/)。

GitHub 首次成功轮询建立基线，不回放历史事件。后续轮询间隔至少 60 秒，观察状态变化，无法提供完整事件流。事件载荷也不能证明运行时已经检出对应版本。

交付工作台就是看板界面。内置泳道包括需求、开发、测试发布、测试验证、生产发布和已完成，自定义看板可以不同。共享批次可能同时移动或发布多张卡片，操作前检查所有成员卡片。当前没有在制品上限控制。

人按项目规则确认范围、处理例外和决定发布。接管会停止自动推进，需要继续时明确交还。触发、看板或提示词不会提供缺失的凭据、按卡片准备的环境或自动业务验收分数。
