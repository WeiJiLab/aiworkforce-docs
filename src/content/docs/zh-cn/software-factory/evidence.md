证据说明交付过程中实际发生了什么。追踪把已确认的需求、执行会话、代码变更、验证结果和后续决定串起来。审阅者可以沿着记录核对哪些结论有证据支持。

## 把记录分开

| 记录                    | 它能支持的结论                           |
| ----------------------- | ---------------------------------------- |
| 已确认的需求            | 约定的范围和验收标准                     |
| 会话                    | 员工被要求做什么，以及哪些工具运行了     |
| Pull Request 或代码引用 | 改变了什么                               |
| 测试或构建记录          | 在哪个版本和环境运行了哪些检查，结果如何 |
| 运行审计                | 该次调用的自动化状态、输出和错误         |
| 人工决定                | 接受、退回、豁免或接管                   |
| 合并记录                | 哪项变更已合入目标分支                   |
| 发布记录                | 哪个版本已部署到目标环境                 |
| 资源回收记录            | 交付流程使用的资源是否已回收             |

根据实际执行的检查，判断结果覆盖了哪些验收标准。各交付阶段见[审阅与发布](/zh-cn/software-factory/review-release/)。交付工作台之外的任务可参考[审阅结果与产物](/zh-cn/user-guide/artifacts-evidence/)。

## 跟踪一项变更

从卡片出发，依次查看会话 ID、代码引用、相关测试批次和人工决定。核对测试结果对应的版本是否就是测试环境实际运行的版本。缺少必需记录时，保留「未验证」的结论并跟进补证。[从 Issue 到 PR](/zh-cn/recipes/issue-to-pr/)给出了一项小改动的示例。

测试任务发现缺陷时，如果团队在预期版本上执行了约定的检查，并提交了必需的报告和日志，测试任务仍可满足验收标准。如果测试脚本执行成功但缺少必需日志，先补齐日志或重新测试，再验收该任务。

发生故障时，可通过[可观测性](/zh-cn/software-factory/observability/)定位记录。[审计与合规](/zh-cn/operate/audit/)说明如何查看谁发起了运行，以及平台保留了哪些内容。
