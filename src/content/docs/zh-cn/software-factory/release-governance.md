发布治理是合并、生产发布和清理的策略：哪条结果可以继续，以及谁仍然负责。审阅者穿过这些记录的路径是[审阅与发布](/zh-cn/software-factory/review-release/)。本页不重复那条路径。工作台仍把结果记在批次和卡片上，已关闭的批次不是生产部署。

## 三个结果

1. **合并。** 当项目有可用的仓库集成且执行员工已授权时，通过的批次可以合并。批次记录合并结果。
2. **生产发布。** 生产发布泳道的独立编排可以按配置的发布日历和目标部署已合入的变更。合入后到卡片上核对生产结果。
3. **清理。** 资源清理沿已完成泳道进行。失败的清理保持可见。它不会改写一次已经成功的发布，成功的发布也不掩盖失败的清理。

自定义看板可能以不同方式安排这些步骤。遵循已配置的泳道。审阅者穿过同一批记录的路径是[审阅与发布](/zh-cn/software-factory/review-release/)。

## 必须已经成立的事实

自动合入和生产部署需要可用的仓库与流水线集成，以及相关员工授权。分别检查批次对**合入**和**生产部署**的必需审批。未配置时，初始审批列表为空。某个动作未配置必需审批时，满足其他条件后可以自动推进。测试豁免备注不能满足测试门禁或审批。

接管卡片会停止自动推进。在期望发布泳道继续之前，明确交还。结束平台对 Pull Request 的跟进不会关闭外部 Pull Request。

这些凭据的边界见[安全与权限](/zh-cn/deployment/security/)。流水线如何挂接见 [CI/CD 集成](/zh-cn/software-factory/cicd/)。
