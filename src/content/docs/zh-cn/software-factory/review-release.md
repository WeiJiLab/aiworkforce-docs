审核确认特定变更是否满足已确认需求，发布确认已接纳变更是否到达目标环境。在交付工作台中，应逐步查看实际记录，避免根据卡片会话或已有 PR 推断整个交付已经完成。

## 准备可审核的变更

在交付工作台打开卡片，阅读当前需求、验收标准、可改仓库和执行记录。沿记录中的分支、提交或 PR 引用查看代码，确认正在审核的代码正是已有证据覆盖的代码。

先检查范围：变更是否解决了约定问题，是否修改了允许边界以外的内容？再检查行为：与验收标准相关的正常输入、输入缺失、权限和失败场景。记录不完整时，应要求补充针对性证据。

## 分开核对交付阶段

内置交付流程会记录多种结果：

| 阶段     | 应查看的内容                                 |
| -------- | -------------------------------------------- |
| 开发     | 代码引用、变更文件、员工总结与已执行检查。   |
| 测试准备 | 候选批次成员、仓库和配置的测试部署。         |
| 测试     | 成员卡片结果，以及实际验证的修订或候选版本。 |
| 合入主干 | 已通过批次的实际合并结果。                   |
| 生产发布 | 已合并卡片及相关仓库的发布结果。             |
| 资源回收 | 生产发布后的回收结果；失败可能需要重试。     |

合入主干成功后，批次会关闭。生产发布独立扫描已合并卡片，资源回收随后由完成泳道推进。因此，批次已关闭并不直接代表生产发布或资源回收已经完成。自定义看板可能采用不同安排，应以配置的泳道和记录为准。

## 作出精确的人工决定

卡片出现问题或批准请求时，先阅读其主题和范围。同意需求确认的是当前需求修订；批准发布动作针对的是该动作，二者不能相互替代。

有用的答复应说明决定、适用范围与依据。例如：“同意当前需求，仅限前端仓库，保留服务端已有名称规则。”若有意免除测试，应写明具体检查、原因、影响范围和未消除风险，避免只说“继续”。

批次级答复可能让全部成员卡片恢复执行。在批准或重试共享工作前，先查看批次成员。提交决定只是继续执行，最终结果仍取决于后续验证和流程规则。

## 处理阻塞或被拒绝的变更

根据当前阻塞原因和执行记录，判断员工需要补充说明、修正凭据、修改代码，还是转人工调查。配置的流程可以将测试失败的工作交回开发。在检查当前执行前，应避免另开并行修复会话。

人工接管后，记录已经完成的处理，并在准备就绪时通过可用恢复操作明确交回。解除暂停不会清除接管状态。结束平台对 PR 的跟进不会关闭外部 PR；卡片仍处于人工处理，直到明确交回。

## 如实说明交付状态

说明验证了哪条需求和哪个代码引用、执行了哪些检查，以及发布记录证实了什么。合并成功但部署失败时，应分别报告。如果发布成功后回收失败，应保留可见的回收问题，同时准确表述发布结果。

自动合并和发布依赖项目真实的代码平台与流水线集成、执行资源及员工授权。创建交付卡片本身不会提供这些权限。
