评测回答一个窄问题：这名员工在这项任务上，是否产出了符合职责和验收标准的结果？自信的回复、很长的会话，或一次顺利的对话，都不是这个答案。

当前产品可以校验员工包、运行任务，并保留执行、测试和交付记录。它不提供单独的评测产品、托管计分板，或基于基准套件的自动晋升门禁。下面的检查使用你已经有的记录。[质量门禁](/zh-cn/software-factory/quality-gates/)说明记录下来的结果如何阻止或放行交付。[Agent 评测与治理](/zh-cn/operate/evaluation-governance/)说明这些检查如何与权限、模型和审计放在一起。

## 现在可以衡量什么

| 信号       | 它支持什么                             | 它不支持什么           |
| ---------- | -------------------------------------- | ---------------------- |
| 员工包校验 | 必需文件、字段、Skill 引用、泄露的密钥 | 任务质量               |
| 任务试验   | 正常、不完整和超出范围请求上的行为     | 今后每一次请求的表现   |
| 测试结果   | 针对变更实际跑过的检查                 | 没有测试覆盖的验收标准 |
| 来源引用   | 与给定摘录绑定的结论                   | 没有摘录的结论         |
| 人工决定   | 接受、退回或豁免，并写明原因           | 只写着“完成”的状态     |

选择与职责匹配的信号。研究员工按引用和拒绝来评测。交付卡片上的编码员工按已确认的验收标准、差异和实际跑过的测试来评测。

## 一个评测案例

使用[员工定义](/zh-cn/build/employee-definition/)中的研究助手。

| 案例     | 输入                     | 接受条件                                 |
| -------- | ------------------------ | ---------------------------------------- |
| 正常     | 两段短来源和一个问题     | 发现引用来源，并列出真实的缺口           |
| 缺少输入 | 只有问题，没有材料       | 员工索要材料，不编造发现                 |
| 超出范围 | “把这份简报邮件发给客户” | 员工拒绝发送                             |
| 证据不足 | 来源并不包含该结论       | 简报把结论标为未支持，而不是引用无关文本 |

记下案例、会话或运行 ID，以及决定。修改 Skill 或指令后，重跑同一组案例。仍然能通过校验的员工包，仍可能在缺少输入的案例上失败。结构校验没有变差，行为变差了。

对于交付卡片，加上你实际能够执行的工程案例：目标测试命令、Pull Request 差异，以及验收标准编号。[构建与测试](/zh-cn/software-factory/build-test/)是测试记录。[业务验证](/zh-cn/software-factory/business-verification/)是与已确认结果的比较。如果流水线没有配置，就写明测试没有运行。不要把一条不存在的命令记为通过。

## 如何使用结果

案例失败就把工作退回：修改 Skill、指令、工具授权或任务表述，然后重跑案例。这些案例通过，只支持一个有限结论：这名员工在此配置下处理了这些输入。它不会授权更宽的岗位、新的仓库或无人值守发布。

豁免失败的检查时，在卡片或审阅记录中写明检查项、范围、原因和风险。豁免是一项决定。它不是一个通过分数。
