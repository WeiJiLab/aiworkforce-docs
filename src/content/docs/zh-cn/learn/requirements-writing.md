好的需求让提出变更的人和实施变更的数字员工对同一个可观察结果达成一致。应在授权开发前写清需求。本指南以假设的校验提示修改说明方法；示例描述的是拟议变更，不代表 AI Workforce 已承诺提供该功能。

## 先建立共同背景

将产品背景和本次变更分开。说明产品的使用者、他们当前遇到的问题、团队希望得到的结果，以及影响方案的约束。已有调研或项目文件可以直接引用，无需在每张任务中复制整篇背景材料。

例如：“工作空间管理员不知道员工名称为什么被拒绝。我们希望他们不离开创建流程就能修正输入。”这解释了修改的原因。“重写整个创建弹窗”则提前指定了实现，并在问题尚未确认时扩大了范围。

第一条需求至少需要说明：

| 背景       | 需要回答的问题                         |
| ---------- | -------------------------------------- |
| 用户与问题 | 谁受到了阻碍，正在尝试完成什么？       |
| 当前行为   | 现在会发生什么？提供可复现示例或来源。 |
| 目标结果   | 修改后，用户应该能够完成什么？         |
| 约束       | 涉及哪些仓库、数据、兼容规则和权限？   |
| 确认人     | 谁负责答疑并确认需求？                 |

明确标注假设和未知事项。缺乏依据的猜测应先成为问题，不应悄悄变成开发指令。

## 用稳定引用描述一个功能

先写简短概述，解释可能产生歧义的术语，再列出少量需求。给每条需求一个在修改措辞后仍保持稳定的编号。下面的编号只是写作约定；AI Workforce 不要求这种语法，也不会据此自动创建记录。

```markdown
## 目标

工作空间管理员可以在提交前修正空白员工名称。

## 术语

空白名称：空值，或仅包含空白字符的值。

## REQ-NAME-01 — 解释空白名称

面向正在创建员工的工作空间管理员，解释空白名称无法提交的原因，
使其能够补充有效内容。

AC-NAME-01.1：名称仅包含空白字符时，在名称输入框旁显示约定的提示。
AC-NAME-01.2：用户输入非空白名称后，清除该提示。
AC-NAME-01.3：名称为空白时，不创建员工实例。

## 本次不处理

不修改模板发现、名称规则或已有员工。

## 允许修改的仓库

仅限约定的前端仓库。
```

每条验收标准只描述一个行为。把“快速”“正确”“妥善处理错误”等词，改写成审核者能够观察的条件和结果。若性能是目标，应先约定测量方式和环境，避免在实现时临时发明指标。

## 补充需求之间的规则

在逐条验收标准之后，解释相互影响：前置校验失败后会发生什么、采用哪个默认值、重试是否可能重复创建内容、权限不足时如何表现。区分必须满足的行为和可选改进。

可以独立验收的结果适合拆开。彼此缺一就无法工作的修改适合一起交付。可选扩展可以后续处理，不应藏在一个小修复的验收标准里。

## 在 AI Workforce 中确认草稿

从工作空间任务收件箱打开适合的事项，通过工作台操作在目标项目中准备草稿。在需求会话中核对需求、验收标准和可改仓库。当前修订准备就绪后，通过卡片上的需求确认请求答复。

员工发现重要缺口时，应先完善草稿再确认。确认需求确立了双方约定的工作，但不会授予缺失的仓库凭据，也不会让尚未配置的交付流水线自动可用。

完成后，你应得到经过确认、有明确边界的需求，其他人能够据其验收或拒绝交付变更。继续阅读[设计与执行计划](/zh-cn/learn/blueprints-work-orders/)和 [Issue 到 PR](/zh-cn/recipes/issue-to-pr/)。
