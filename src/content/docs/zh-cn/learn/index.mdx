实践手册说明在员工行动之前如何框定工作。范例沿着一条路径，从请求走到经过审阅的结果。它们曾经是独立的 Learn 入口。现在放在资源中，与使用同一套词的产品指南放在一起。

## 从你要做的决定开始

- [需求写作](/zh-cn/learn/requirements-writing/) — 写下结果，以及人可以检查的验收标准。
- [方案与工作单](/zh-cn/learn/blueprints-work-orders/) — 把设计说明和执行任务分开。平台不提供 Blueprint 模块。
- [反馈与审阅](/zh-cn/learn/feedback-review/) — 判断一条发现是缺陷、新范围，还是一个问题。
- [从 Issue 到 Pull Request](/zh-cn/recipes/issue-to-pr/) — 把一项工程请求带过确认、执行、验证和审阅。
- [最佳实践](/zh-cn/resources/best-practices/) — 这些指南里反复出现的短规则。

## 把工作交回产品

实践手册不会创建员工或流水线。需求清楚之后，用[数字员工](/zh-cn/user-guide/ai-employees/)分配任务；结果是代码变更时，使用[软件工厂](/zh-cn/software-factory/overview/)。需要新岗位的构建者继续阅读[员工定义](/zh-cn/build/employee-definition/)。

确认任务之前，团队应能说出结果、允许的范围、可观察的验收检查，以及必须由人决定的位置。如果某个答案缺失，就去要这个答案。如果答案改变了范围，先更新需求，再继续执行。
