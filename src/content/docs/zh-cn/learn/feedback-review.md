客户反馈和监控信号是做决定的输入。在让员工实施变更前，先明确实际观察到了什么、是否能够复现，以及团队希望改善什么结果。AI Workforce 通过工作空间任务收件箱提供研判入口；本指南不假定存在独立的反馈主题模块。

## 保留原始观察

打开采集或导入的事项，阅读来源、说明和已有证据。区分报告者的原话和员工的解释。“编辑名称后提交操作似乎不可用”是观察；“数据库坏了”在获得证据前仍是假设。

记录受影响的用户或角色，避免暴露不必要的个人信息，并补充相关时间或版本、操作步骤、实际结果和期望结果。审核者能够访问原始材料时，应提供来源链接。报告不完整时先请求补充，不要虚构复现步骤来填空。

## 先研判，再实施

按照事项工作流和当前权限使用可用操作：

| 决定       | 适用情形                                         |
| ---------- | ------------------------------------------------ |
| 请求补充   | 报告缺少开展调查所需的背景。                     |
| 接纳       | 观察有价值，值得继续跟进；接纳本身不会开始编码。 |
| 标记重复   | 已有事项负责同一问题，同时保留原始来源。         |
| 暂缓       | 需要稍后重新评估，并设置有意义的复查时间。       |
| 忽略或归档 | 按可用工作流记录不再继续处理的理由。             |

一条报告可能包含多个问题。必要时保留来源事项，再派生有明确目标的行动事项。不要因为请求来自同一次会议或同一渠道，就合并本不相关的工作。

## 核对自动采集

自动化配置了「收集任务 / Issues」时，应检查运行的采集回执。会话总结里说“已保存”并不充分。保存成功必须返回真实事项标识，空结果也应有单独的完成记录。保存失败应如实表现为失败。

反复检查同一来源时，应使用稳定的来源标识。以前某次运行采集成功，不能证明当前运行已经更新事项。明确配置结果去向：进入工作空间收件箱等待研判，或进入能够为合适事项创建交付草稿的工作台项目。不支持开发的事项仍保留在收件箱中。

## 创建有边界的后续工作

支持开发的事项可以通过工作台操作选择目标项目。阅读草稿、确认可改仓库，并将报告整理成[可验证的需求](/zh-cn/learn/requirements-writing/)。需求员工与人共同澄清并确认后，工作才进入开发就绪状态。

如果采集器已经在目标工作台创建草稿，应沿该链接继续，不要再建一张卡。拿不准时，检查采集回执和事项关联的交付状态。

## 让交付结果回到反馈

交付后，把记录的结果与最初观察对照。对外说明改动时，关联实际代码或发布证据。已采集事项、已完成会话、已在生产修复的故障含义不同，应按证据支持的状态表述。

新报告揭示不同问题时，应保留为新工作，避免悄悄扩大已经完成的任务。继续阅读[收件箱与任务](/zh-cn/user-guide/inbox-tasks/)和[审核与发布](/zh-cn/software-factory/review-release/)。
