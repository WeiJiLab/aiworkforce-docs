经过确认的需求说明用户需要什么结果，技术设计解释系统如何实现这个结果，执行计划则把有明确边界的一部分变更交给员工。保持三者关联，可以避免实现满足了一个方便的解释，却偏离了真正的需求。

本指南中的 **Blueprint（蓝图）** 指团队维护的技术设计文档。AI Workforce 当前没有独立的 Blueprint 模块，也不会解释 8090 的组件引用语法。平台另有与委派工作关联的编排工作单；它们与软件工厂交付卡片、以及被称为工作单的规划文档是不同概念。

## 从已确认的需求出发

在选择组件、拆分工作之前，先阅读需求与验收标准。打开来源引用，并记录本次规划采用的修订。如果变更仍有歧义，应把问题交回需求负责人确认。

对[需求写作](/zh-cn/learn/requirements-writing/)中的校验提示示例，设计应解释在哪里检查空白输入、如何清除提示。不能因为开发者发现了相邻代码，就顺带引入新的名称规则。

## 编写能够对应真实代码的设计

小变更可能只需几段说明。跨越多个边界的变更，则应覆盖以下内容：

| 部分       | 有用的信息                                 |
| ---------- | ------------------------------------------ |
| 背景与范围 | 需求引用、受影响行为与排除项。             |
| 当前行为   | 仓库中实际观察到的组件与契约。             |
| 拟议流程   | 每项决策由哪个组件负责，边界之间传递什么。 |
| 数据与访问 | 输入、状态变化、授权与敏感值。             |
| 失败行为   | 校验错误、中断和安全重试的预期。           |
| 验证方式   | 哪些检查能够证明各条验收标准。             |
| 待决事项   | 仍需人工决定的问题。                       |

引用真实存在的源码路径和符号，将拟新增组件明确标为提议。实现理由写在设计里，同时保持需求已约定的含义。把文档保存在适当的仓库或项目文件中，并在需求会话或卡片材料中提供引用；仅有文件名不会自动建立动态依赖图。

## 明确执行边界

可执行的任务需要目标、负责范围、排除项、必要背景、允许使用的资源，以及应返回的证据。例如：

```text
目标：按约定的校验行为满足 REQ-NAME-01。
范围：已有创建表单及其相关校验测试。
排除：后端名称规则、模板发现、已有员工。
开始前阅读：已确认需求和此处引用的设计修订。
资源：已批准的前端仓库；不增加凭据。
返回：变更文件或代码引用、已执行的检查、结果和缺口。
若需求与当前行为冲突，先提问，不自行扩大范围。
```

只带入当前任务负责的验收标准，保留编号及含义。不要按任意文件数量拆分任务，而应在结果可独立检查、下一项工作依赖明确的位置拆开。

## 在工作台中应用计划

通过交付卡片的需求和关联会话，将约定设计与范围带入执行。在项目配置中确认可改仓库和泳道员工。设计中提及某个仓库，并不等于授权员工使用其凭据。

实现后，对照需求与设计检查实际变更。若技术决策发生变化，记录原因和新的引用；若用户需要的结果变化，则应重新澄清需求，避免悄悄改写验收标准来迎合已有实现。
