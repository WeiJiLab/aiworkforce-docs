把已有的工程方法变成可复用的员工能力，再通过一项自动化实际运行。需要的角色或方法还未准备好时，使用本课程。看板已有合适员工时，可以直接从[快速入门](/zh-cn/getting-started/quickstart/)开始。

## 本课程构建什么

继续[基础课程](/zh-cn/learn/software-factory-foundations/)中的表单校验案例。团队需要一名员工调查相似请求，形成可审阅的建议。输入包括 Issue、相关项目资料和验收标准；输出应说明受影响的行为，以及还需要哪些证据。请求在交付卡片上确认后，才开始实施。

## 按这个顺序构建

| 阶段               | 检查产出                                           | 权威操作指南                                                                                        |
| ------------------ | -------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 明确职责           | 写清必需输入、预期输出、不负责的工作和验收标准     | [员工定义](/zh-cn/build/employee-definition/)                                                       |
| 准备访问           | 员工在授权范围内使用指定仓库和工具                 | [代码仓库](/zh-cn/integrations/code-repositories/)与[员工工具](/zh-cn/integrations/employee-tools/) |
| 试验真实请求       | 正常请求、缺失输入、超出职责三类案例均有可接受行为 | [员工测试](/zh-cn/build/testing/)                                                                   |
| 发布并创建实例     | 模板版本已发布，工作空间员工准备就绪               | [发布](/zh-cn/build/publishing/)与[创建员工](/zh-cn/getting-started/first-employee/)                |
| 先运行，再自动触发 | 检查一次手动 Job 运行的结果，再启用自动触发规则    | [第一个工作流](/zh-cn/getting-started/first-automation/)                                            |

保留试验的输入、接受的输出和失败案例。能力包校验检查结构，任务试验检查实际行为；这些步骤不表示平台已有自动基准评测服务。发布模板与启用 Job 是不同操作，既有员工采用新版本也需要明确安排。

## 怎样算完成

你能指出模板版本、一名就绪的工作空间员工、记录下来的任务试验，以及一次检查过的手动运行。你知道后续由哪条规则触发，以及哪些决定仍由人作出。需要让已确认变更经过团队看板交付时，继续[运行软件工厂](/zh-cn/learn/run-software-factory/)。
