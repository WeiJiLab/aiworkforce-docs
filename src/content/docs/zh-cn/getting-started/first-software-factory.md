软件工厂是从已确认的工程请求到经过审阅的变更。这条首次流程只跟一张卡片。它不会打开无人值守的合并或生产发布。这些步骤需要仓库凭据、执行员工和流水线资源，新建一张卡片并不会替你创建它们。

## 前提

你需要一个工作空间、已配置的工作台项目和看板、至少一个仓库连接，以及你将使用的泳道上的就绪员工。执行员工需要对他们应接触的仓库持有授权。工作空间上的仓库连接不等于这项授权。连接尚未就绪时，阅读[代码仓库](/zh-cn/integrations/code-repositories/)。

## 1. 开发之前先确认请求

进入工作台的事项会成为草稿。草稿等待人确认范围、验收标准和允许的仓库。确认需求不会补上缺失的凭据，也不会修好流水线。验收标准仍不清晰时，让卡片保持草稿。

## 2. 让一名员工执行已就绪的卡片

卡片就绪后，从卡片启动或继续开发会话。让允许的仓库和验收标准在这项工作中保持可见。在卡片上回答问题。如果你接管，自动推进会停止，当前状态会保留。希望泳道继续时，明确交还工作。只是恢复暂停，并不能清除接管。

## 3. 要求验证和证据

对话结束不等于交付结束。看板使用内置泳道时，继续跟到测试发布和测试验证。阅读执行记录、代码引用或 Pull Request，以及测试结果。失败的测试可以把工作退回修复。如果你豁免某项检查，写明检查项、原因、范围和剩余风险。

## 4. 在未配置的发布之前停下

只有项目具备可用的仓库和流水线集成时，合并和生产发布才会执行。不要把已关闭的批次当成生产发布或清理已经完成的证明。后续记录见[审阅与发布](/zh-cn/software-factory/review-release/)。

## 预期结果

你能指出一项已确认的需求、完成工作的会话、变更或 Pull Request，以及你用来接受或退回它的证据。完整地图是[软件工厂概览](/zh-cn/software-factory/overview/)。同一条路径上更完整的团队决定，见 [Issue 到 PR](/zh-cn/recipes/issue-to-pr/)。
