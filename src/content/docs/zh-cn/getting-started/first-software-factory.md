首次配置会接上交付看板需要的工具，选择员工在哪里运行，为第一张卡片做好准备。第一次变更之前先连接代码托管。需要把消息或外部事项送上看板时，再连接那些来源。看板已经配好时，直接进入[快速入门](/zh-cn/getting-started/quickstart/)。

你需要在目标工作空间拥有创建交付看板、管理仓库和员工授权的权限。准备一个获准使用的测试仓库、可以验证变更的方法，以及包含需求、开发和验证阶段的已发布看板模板。看板模板缺失时请系统管理员发布。不能添加泳道员工时，页面写的是联系空间管理员。按[创建数字员工](/zh-cn/getting-started/first-employee/)，为每条必配泳道准备一个已就绪的员工实例。

## 让员工访问仓库和交付工具

### 1. 连接代码托管

打开**代码仓库**。通过**管理仓库连接**选择与测试仓库提供方及实例匹配的连接，或使用已获准的工作空间凭据创建连接。选择**添加代码仓库**，核对克隆地址和默认分支。

托管可以是 [GitHub](/zh-cn/integrations/github/)、[GitLab](/zh-cn/integrations/gitlab/)或[云效 Codeup](/zh-cn/integrations/yunxiao/)。令牌、实例和授权的共用规则见[代码仓库](/zh-cn/integrations/code-repositories/)。

为开发泳道员工授予使用该凭据访问允许仓库的权限。其他泳道员工如果要访问仓库，也检查各自的授权。工作空间里的一条连接不会授权每一名员工。先用一个小型读取任务确认访问，再让开发员工修改代码。变更需要产生 GitHub Pull Request 时，员工的允许操作要覆盖创建分支和 Pull Request。

### 2. 连接消息渠道

打开**集成**，连接工作空间目录里列出的渠道。可选项是[飞书和 Lark](/zh-cn/integrations/feishu/)、[钉钉](/zh-cn/integrations/dingtalk/)、[Slack](/zh-cn/integrations/slack/)、[Microsoft Teams](/zh-cn/integrations/microsoft-teams/)、[企业微信](/zh-cn/integrations/wecom/)和[微信](/zh-cn/integrations/wechat/)。

已连接的渠道可以触达主员工。渠道接受入站消息时，允许的发送者可以在一段对话里启动 Job。渠道不会创建交付卡片。报告如何变成工作，见[信号到卡片](/zh-cn/software-factory/signal-to-card/)。第一张卡片将在看板上开始时，可以先跳过这一步。

### 3. 连接事项来源

GitHub 和云效导入使用仓库或项目选择器。管理员接上来源之后，[Jira](/zh-cn/integrations/jira/)和 [Linear](/zh-cn/integrations/linear/)会出现在同一个导入对话框里。导入创建收件箱任务。它不会启动会话，也不会把状态写回跟踪系统。

Job 也可以轮询 GitHub 事项事件。支持的观察是打开、关闭、重新打开、标签和评论。配置见 [Issue 自动化](/zh-cn/workflows/issue-automation/)。第一项请求将用看板上的需求会话开始时，可以先跳过外部来源。

## 给员工一个工作位置

### 1. 选择工具在哪里运行

平台保留对话、模型循环和授权。命令在为该员工配置的环境里运行。创建卡片不会准备虚拟机或预览地址。

| 选项       | 什么时候用                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 平台托管   | 部署已经在运行员工，并且仓库凭据在这个工作空间上。                                                                                           |
| 自托管平台 | 仓库和工具应留在你运营的基础设施上。按[自托管](/zh-cn/deployment/self-host/)操作。                                                           |
| 已授权设备 | 命令应在已配对的 macOS 或 Linux 电脑上运行，以主机用户身份，在获准的工作目录中执行。用 [Device Executor CLI](/zh-cn/integrations/cli/)配对。 |

完整选择见[运行时管理](/zh-cn/deployment/runtime-environments/)。测试结果要写明什么才算证据，见[开发环境](/zh-cn/software-factory/environments/)。确认员工能在你打算使用的环境中运行。

### 2. 为看板命名并指派员工

1. 在主导航打开**工作台**。交付工作台的地址是 `/automations?tab=board-flow`。选中目标工作空间，点击**新建交付项目**，进入**创建看板**向导。
2. 在**选择模板**中选用已发布的交付模板。在**基本信息**中填写看板名称并核对泳道顺序。在**数字员工**中给每条必配泳道分配一名已就绪的员工。需求员工澄清范围。开发员工实现已确认的卡片。测试验证记录结果。生产发布在合并和部署集成可用时执行这些步骤。
3. 在**共享 MCP 与 Skill**中核对模板预选的工具和技能。在**外部看板与工作项来源**中，如果上面的事项来源还没准备好，第一次试跑可以跳过外部同步和来源配置。也可以从任务收件箱转入 Issue，或在看板中新建需求会话。
4. 在**确认创建**中核对配置，点击**创建看板**。模板中的自动化可能在初始化通过后启用，创建前请确认选的是测试工作空间和适用的模板。初始化完成后点击**进入看板**。某个模块失败时可以单独重试；需要调整输入时选择**返回配置**。

尚未保存的新项目在看板设置里显示**观察模式**。页面写着：「新项目先保存为观察模式 · 检查通过后再启动。」先检查配置，再启动项目。

### 3. 核对泳道和验证路径

1. 在**看板设置**中确认项目绑定了测试仓库。创建时如果跳过了外部事项来源，添加该来源之前先绑定仓库。打开**泳道配置**，核对每条必配泳道的**执行身份**。用**泳道流程**核对员工指派和已保存的自动化。
2. 需要自动检查时，连接项目的测试工作流，并核对实际使用的测试部署或环境。已连接的 GitHub 仓库可以使用 GitHub Actions 工作流作为项目流水线。配置方法见 [CI/CD 集成](/zh-cn/software-factory/cicd/)和 [GitHub](/zh-cn/integrations/github/)。从配置好的测试发布和测试验证泳道查看运行结果。
3. 自动检查还不可用时，选定一项可以在测试环境里执行的具体检查，并记录哪些自动检查没有运行。在团队拿到结果或记录明确豁免之前，保持必过门禁处于阻断。见[质量门禁](/zh-cn/software-factory/quality-gates/)。

## 下一步

仓库已绑定、必配泳道都有就绪员工，并且你知道在哪里核对测试结果，就可以选一条小 Issue 开始交付了。[在已有看板上交付第一条 Issue](/zh-cn/getting-started/quickstart/)。
