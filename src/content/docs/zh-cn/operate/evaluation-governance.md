治理是这些控制之间的关系，不是一个设置页面。员工可以在工作空间里可见，却仍然不能调用某个工具。模型可以被选中，却仍然贵得不适合这项任务。测试可以失败，并且只有人把豁免写下来时才能被豁免。本页说明这些控制如何相遇。检查本身在 [Agent 评测](/zh-cn/software-factory/evaluation/)和[质量门禁](/zh-cn/software-factory/quality-gates/)。

## 一名员工，几项决定

| 决定                       | 在哪里作出                                                                              | 提示词不能代替什么   |
| -------------------------- | --------------------------------------------------------------------------------------- | -------------------- |
| 谁可以使用工作空间         | [团队与访问](/zh-cn/administration/teams-access/)                                       | 一个分享链接         |
| 员工可以使用哪些工具和仓库 | 员工授权和[安全与权限](/zh-cn/deployment/security/)                                     | 指令里的“只读”       |
| 工具在哪里运行             | [运行时管理](/zh-cn/deployment/runtime-environments/)                                   | 包里写的一个路径     |
| 用哪个模型、成本是什么     | [模型与成本](/zh-cn/models/overview/)和[平台配置](/zh-cn/administration/configuration/) | 在聊天里输入的模型名 |
| 结果能否继续               | 泳道记录和人工决定                                                                      | 一句自信的结束语     |
| 调用了什么                 | 运行历史和[审计](/zh-cn/operate/audit/)                                                 | 一张对话截图         |

去改拥有这次失败的那项控制。轮换登录令牌不会恢复已撤销的仓库凭据。更新模板不会更新已有实例。一张监控图不会验收交付物。

## 运营这个循环

给员工与岗位匹配的最窄授权。把它路由到部署实际提供的模型。用你能在[用量与分析](/zh-cn/administration/analytics/)里读到的用量来约束工作。门禁打开之前要求证据。当评测显示重复失败时，修改 Skill 或任务表述，并重跑同一组案例。不要放宽授权来掩盖一个坏结果。
