运营工作流，需要检查真实任务是否产生可接受结果，以及维持它运行需要多少投入。先选择一条工作流和一组可比较的小任务，再扩展到更多团队。

## 结合任务阅读结果

检查失败任务，也检查反复依赖人工介入才成功的任务。把任务、员工版本、结果和验收决定放在一起。用量记录帮助解释投入，业务结果仍需要团队确认。

例如，报告审阅员总要人在回复后追问来源，可能说明输出方法不完整。如果执行从未访问到来源系统，应先检查连接或权限。

## 选择具体改进项

| 要回答的问题                     | 从哪里查看                                                                                           |
| -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 任务为何停止或需要帮助？         | [运行与恢复](/zh-cn/automate/runs-recovery/)和[可观测性](/zh-cn/software-factory/observability/)     |
| 新版本应通过哪些案例？           | [执行评测](/zh-cn/software-factory/evaluation/)                                                      |
| 实际能观察到哪些模型用量和成本？ | [模型与成本](/zh-cn/models/overview/)和[用量与分析](/zh-cn/administration/analytics/)                |
| 谁能使用资源、作出关键决定？     | [平台治理](/zh-cn/operate/evaluation-governance/)和[团队与访问](/zh-cn/administration/teams-access/) |

修改能够解释这次失败的工作方法、任务输入、工具连接或对应控制。不要扩大权限来掩盖不合格结果。

## 扩大范围之前先复验

修改后重跑相关案例，包括过去的失败案例。比较被接受的结果、返工、人工接管，以及使用的投入。业务周期和全部人工投入可能需要团队自行记录，平台用量不会自动计算投入产出比。

明确安排新版本的采用，并检查工作空间中的实际实例。这是团队持续改进流程，不表示自动学习或自动更新所有员工。

## 怎样判断有了改进

团队能够说明解决了哪类失败、重复检查了哪些案例、采用了哪个版本，以及还有什么限制。当前工作流达到约定标准后，再扩展到下一类任务或团队。

用[执行评测](/zh-cn/software-factory/evaluation/)定义下一次比较。新的工作流应先[准备交付看板](/zh-cn/getting-started/first-software-factory/)，再衡量运行情况。
