本案例跟随一个小缺陷，从工作空间收件箱进入交付卡片，再检查代码评审证据。建议选择修改校验提示语等影响较小的任务，目标是得到一项需求明确、验证可追溯的变更。

## 前置条件

你需要一个有执行员工的工作空间、支持转开发交付的 Issue，以及已经配置好的工作台项目。代码仓库、泳道员工和所需测试流水线应已就绪；工作空间凭据需要显式授权给实际使用它们的执行员工。

## 1. 检查 Issue

从工作空间管理打开「收件箱」，阅读来源、描述与观察记录。确认问题可以复现，并且属于当前工作空间。

例如，项目表单在名称留空时只提示「输入无效」。在 Issue 中写明出现问题的表单、复现步骤，以及期望的提示 `请输入项目名称。`。如果 Issue 来自自动化采集，可在采集回执中查看来源详情。

## 2. 转为工作台草稿

使用 Issue 的转工作台操作，选择预期项目并确认去向。生成的卡片是**待人工确认的草稿**；转入工作台不等于授权立即开发。

打开关联草稿，澄清以下内容：

- 具体需要改变的行为，以及不属于本次任务的范围。
- 可以检查的验收标准。
- 允许改动的代码仓库。

这项修改有两条验收标准。名称留空提交时，页面显示 `请输入项目名称。`。填写有效名称后，表单仍可正常提交。

通过卡片当前的人工请求完成需求确认。如果还需要澄清，在关联需求会话中继续补充。

## 3. 跟踪执行

打开交付工作台，检查卡片进度与执行会话。配置好的泳道编排会接走就绪工作。遇到问题、审批、权限不足或测试失败时，根据记录的阻塞原因处理。

需要人工调查时，先接管并留下明确的处理决定。解决问题后，显式交回自动流程。共享批次可能还有其他卡片，执行批次操作前先核对成员。

## 4. 检查代码与证据

打开卡片交付物，查看其中记录的代码引用。根据项目的代码平台集成和交付路径，引用可能指向分支、提交或 PR。核对代码差异是否符合已确认的范围。针对提示语修改，在项目测试环境中分别验证两种提交情况，并记录环境、实际测试的提交和每条验收标准的结果。如果项目按批次测试，记录实际部署到测试环境的候选版本。

如果某项检查失败，退回变更时附上复现步骤和测试结果。修复后，在新提交上重新执行检查，并关联新的结果。记录审阅决定，并关联作为依据的版本证据。

如果项目还配置了合并和发布，分别核对这两项记录。确认实际部署到生产环境的版本，再检查资源回收结果。各阶段的记录见[审阅与发布](/zh-cn/software-factory/review-release/)。
