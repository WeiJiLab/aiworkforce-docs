项目表单在名称留空时只提示「输入无效」。团队希望给出更明确的提示，第一次验证时却发现正常提交也失败了。本案例展示如何从收件箱接手这条 Issue，并在修复后作出审阅决定。

下文中的卡片、代码引用和验证结果均为示例，无需登录即可阅读。要在自己的工作空间动手，按[快速入门](/zh-cn/getting-started/quickstart/)操作。

## 1. 检查 Issue

在工作空间的「收件箱」读这条 Issue 的来源和复现步骤。审阅者打开项目表单，留空名称并提交，确认页面显示通用提示，并找到需要修改的前端仓库。若 Issue 由自动化采集，可以打开采集回执核对来源。

## 2. 转为工作台草稿

使用 Issue 的转工作台操作，选择目标项目。在生成的草稿上写明范围和验收标准。本例只允许改动前端仓库，保留服务端校验规则。

| 验收项 | 预期结果                               |
| ------ | -------------------------------------- |
| AC1    | 名称留空提交时显示 `请输入项目名称。`  |
| AC2    | 填写有效名称并提交后，能正常创建项目。 |

审阅者检查两条验收标准，通过卡片上的人工请求确认范围和允许修改的仓库。确认后，交付流程才会推进。有疑问时，先在关联需求会话中澄清。

## 3. 跟踪执行

从 **Automations** 打开交付工作台（`/automations?tab=board-flow`），进入卡片查看开发会话，并在卡片上回答问题或处理审批。本例中的交付卡片关联了前端仓库的 PR。不同仓库集成和交付路径也可能提供分支或提交引用。

需要人工调查时，先接管并留下明确的处理决定。解决问题后，显式交回自动流程。共享批次可能还有其他卡片，执行批次操作前先核对成员。

## 4. 验证、退回与复验

从卡片打开代码引用，按已确认的范围审阅 diff。再到测试环境检查两种提交结果。按批次测试的项目需要记录实际部署到测试环境的候选版本。审阅者可以在卡片上记录如下结果，关联对应检查或观察记录。

| 受测版本   | 环境         | 验证证据                                                                   | 审阅决定                                              |
| ---------- | ------------ | -------------------------------------------------------------------------- | ----------------------------------------------------- |
| 候选版本 A | 项目测试环境 | 构建通过。AC1 通过。AC2 失败，提交有效名称后表单仍停留在原处，项目未创建。 | 附上 AC2 的复现步骤和结果，退回开发。                 |
| 候选版本 B | 项目测试环境 | 构建通过。AC1 显示了新的提示。AC2 创建项目并显示项目详情。                 | 接受候选版本 B 在约定范围内的变更，关联两条验收记录。 |

修复后，审阅者在候选版本 B 上重新验证两条验收标准，记录新的审阅决定。现在，卡片关联了已确认的 Issue、开发会话与代码引用、各受测版本的证据，以及接受修复的决定。

如果项目还配置了合并和发布，请分别核对实际合并的变更、部署到生产环境的版本，以及资源回收结果。各阶段的记录见[审阅与发布](/zh-cn/software-factory/review-release/)。
