本案例跟随一个小缺陷，从工作空间收件箱进入交付卡片，再检查代码评审证据。建议选择修改校验提示语等影响较小的任务，目标是得到一项需求明确、验证可追溯的变更。

## 前置条件

你需要一个有执行员工的工作空间、支持转开发交付的 Issue，以及已经配置好的工作台项目。代码仓库、泳道员工和所需测试流水线应已就绪；工作空间凭据需要显式授权给实际使用它们的执行员工。

## 1. 检查 Issue

从工作空间管理打开「收件箱」，阅读来源、描述与观察记录。确认问题可以复现，并且属于当前工作空间。

例如，说明现有校验提示、期望替换文字，以及出现问题的页面。补充其他人能够照做的验证步骤。如果 Issue 来自自动化采集，检查采集回执，不要只依据运行会话中的总结。

## 2. 转为工作台草稿

使用 Issue 的转工作台操作，选择预期项目并确认去向。生成的卡片是**待人工确认的草稿**；转入工作台不等于授权立即开发。

打开关联草稿，澄清以下内容：

- 具体需要改变的行为，以及不属于本次任务的范围。
- 可以检查的验收标准。
- 允许改动的代码仓库。

通过卡片当前的人工请求完成需求确认。如果还需要澄清，在关联需求会话中继续补充。

## 3. 跟踪执行

打开交付工作台，检查卡片进度与执行会话。配置好的泳道编排会接走就绪工作。遇到问题、审批、权限不足或测试失败时，根据记录的阻塞原因处理。

需要人工调查时，先接管并留下明确的处理决定。解决问题后，显式交回自动流程。共享批次可能还有其他卡片，执行批次操作前先核对成员。

## 4. 检查代码与证据

打开卡片交付物，跟随记录的分支、提交或 PR 引用，检查真实 diff 与测试结果是否满足已确认的验收标准。是否生成 PR 取决于配置的代码平台集成与交付路径，应以真实记录为准。

如果项目还配置了合入与发布，继续检查这些后续环节的结果。关联了 PR，或员工回复「已完成」，都不能单独证明测试、合入或生产发布已经完成。
