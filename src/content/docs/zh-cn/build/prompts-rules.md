提示词应说明岗位、当前任务，以及如何判断结果合格。把可复用的岗位指令与单次请求的输入分开，员工才能稳定处理不同样例。

## 选择指令层

| 层次       | 应放内容                               | 维护位置                                |
| ---------- | -------------------------------------- | --------------------------------------- |
| 员工岗位   | 职责、场景、不负责范围、必需输入与输出 | 员工定义与已发布模板。                  |
| 员工档案   | 当前实例的职责和适合承接的任务         | 员工档案 → 岗位，需要工作空间管理权限。 |
| 可复用方法 | 可重复任务的步骤、检查与输出格式       | 包中的 `skills/<skill-id>/SKILL.md`。   |
| 自动化任务 | 已注册任务及其输入输出约定             | Job 草稿及随后发布的版本。              |
| 交付泳道   | 该泳道执行员工的工作指令               | 看板的泳道配置。                        |
| 当前请求   | 目标、已知事实、范围与验收标准         | 会话消息或 Job 声明的输入。             |

实例创建时会复制岗位档案字段。之后修改档案，不会回写源模板；修改模板，也不能证明已有实例已经应用变更。

## 编写可以验收的任务

例如，给文档审核员工的任务可以写成：

```text
检查所提供的快速入门，找出新用户无法跟随的步骤。
只使用提供的页面及已说明的产品行为。
返回表格：不清楚的步骤、缺少的前置条件、建议修订。
不确定的产品行为以问题标注。
不要编辑或发布页面。
```

把待检查的页面作为输入提供，不让页面正文重新定义员工职责。明确可以使用的来源，以及哪些内容仍需确认。对于 Job，任务指令留在配置中，调用输入遵守声明的 Schema；调用者不能通过执行 API 替换运行配置。

## 理解仓库规则

AI Workforce 没有为 Cursor Rules、Augment 指令及所有 IDE 设置提供通用导入器。使用 Claude Code 运行时时，项目指令遵循该运行时支持的配置来源。平台管理的实例指令可能生成到 `CLAUDE.md`，不要把该生成文件当成员工包的源定义。

员工包校验会拒绝根目录 `CLAUDE.md`。岗位和路由维护在 `.aiworkforce/`，工作方法放在技能中，仓库贡献者指令放在 `AGENTS.md`。不要为了通过包校验新增第二套指令层级。

## 检查实际行为

通过会话的系统提示词查看入口，检查你有权限查看的组装结果。核对员工、工作空间和泳道上下文，不要假定最后编辑的文本一定已生效。分别测试正常请求、输入不足和来源文本与任务冲突的情况。

自然语言规则用于指导行为；工作空间权限、员工凭据授权、工具授权和审批才是访问控制的执行机制。提示词写了「只读」，不能替代为任务选择适当的工具与凭据。
