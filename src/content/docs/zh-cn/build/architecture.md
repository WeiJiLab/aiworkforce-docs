数字员工是一项带版本的专业能力，被放到可以行动的运行时里。它拥有明确的岗位和使命，以及完成工作所需的 Skill、知识、工具和工作流规则、明确的权限和评测方法。执行产生的证据让团队可以决定工作是否能够继续。

构建者用这个模型定义岗位。使用者遇到的是从已发布模板创建的工作空间员工。创建流程配置的是一个实例，不会替代源 Agent 包。

## 员工模型

| 产品概念     | 它回答什么问题                         | 当前落在哪里                             |
| ------------ | -------------------------------------- | ---------------------------------------- |
| Role 岗位    | 这名员工承担什么专业职责？             | `employee.yaml` 与 `router.md`           |
| Mission 使命 | 员工对什么结果负责？                   | 岗位目标、任务契约和验收标准             |
| Skill        | 员工使用什么可重复的方法？             | `skills/` 与引用的指令                   |
| 知识与记忆   | 员工可以使用哪些项目和组织上下文？     | 项目文件、工作空间上下文和经过审阅的记忆 |
| 工具         | 员工可以调用哪些操作？                 | 插件元数据、工具声明和 MCP 依赖          |
| 工作流       | 员工按什么顺序和交接方式工作？         | 会话流程、协作模板和交付看板             |
| 触发条件     | 什么会启动一次运行？                   | 人、事件、日程或交付泳道                 |
| 权限         | 哪些资源和操作获得授权？               | 工作空间授权、连接和运行时身份           |
| 评测         | 人如何判断结果合格？                   | 测试、审阅发现、质量门禁和证据           |
| 生命周期     | 员工如何构建、发布、使用、评测和改进？ | 构建、模板、实例、运行和修订记录         |

这些部分共同组成一名员工。没有岗位的 Skill 只是没有工作的办法。没有工具授权的岗位只是意图。没有验收标准的工作流没有清晰的终点。没有证据的执行只是一段对话。

## 岗位与使命

岗位命名一项专业职责。使命说明什么结果才算有用。范围说明这项工作可以接触哪些输入和系统。调用规则说明何时应该选择这名员工，以及请求应交给别处的情况。

这条链路是[Agent 定义](/zh-cn/build/employee-definition/)的主干：

`岗位 → 使命 → Skill 与知识 → 工具与工作流 → 权限 → 评测`

总结给定材料的研究助手，和发布这些材料的员工，不是同一个岗位。把排除项写进岗位和使命，再用授权与审阅门禁执行边界。

## Skill、知识与记忆

Skill 描述带有输入、步骤和输出的可重复方法。知识提供应用这些方法所需的项目和组织上下文。记忆是工作空间保存并可以审阅的上下文，不是隐藏的第二份指令文件。

稳定策略属于岗位。当前目标、文件和验收标准属于会话。[Agent 指令](/zh-cn/build/prompts-rules/)说明该改哪一层。自然语言策略不会授予访问权。

## 工具、工作流与触发条件

工具是运行时被允许执行的一项操作。MCP 服务是岗位预期要调用的外部服务。工作流描述执行顺序、交接和人工决定。触发条件让一次运行从人、事件、日程或交付泳道启动。

清单中的 `mcp_servers` 只有名称和描述。连接配置、安装、账号授权和运行时位置是分开的步骤。构建者见 [MCP 服务](/zh-cn/build/mcp-integration/)，操作者见 [MCP 集成](/zh-cn/integrations/mcp/)。不要把凭据放进 Agent 包。

[Skills](/zh-cn/build/skills/)和[Plugins](/zh-cn/build/plugins/)给出目录结构。[工具](/zh-cn/build/tools/)区分声明的工具和已授权的工具。

## 权限与执行

已发布模板变成工作空间实例。实例必须完成初始化，会话才能开始。会话保存对话和执行上下文，包括为这次运行准备的能力。工具在已配置的运行时中执行，可以是平台执行，也可以是已授权设备。工作空间授权和运行时身份共同决定员工实际能访问什么。见[运行时管理](/zh-cn/deployment/runtime-environments/)和[安全与权限](/zh-cn/deployment/security/)。

[Agent 组合](/zh-cn/build/composition/)说明主 Agent 与子 Agent。在正文里提到 subagent，并不能证明运行时调用了它。交还给人的步骤是[人工确认](/zh-cn/user-guide/human-approval/)，不是另一个隐藏的 Agent。

## 评测与生命周期

Agent 包校验检查结构：必需文件、清单字段、Skill 引用，以及是否暴露凭据。它不能证明员工把工作做好了。[员工测试](/zh-cn/build/testing/)用来尝试正常请求、缺失输入和超出范围的请求。[发布](/zh-cn/build/publishing/)把经过检查的 Agent 包放到工作空间可以创建实例的位置。

评测在发布之后仍会继续。保留有代表性的案例，在岗位、Skill、知识、授权或模型路由变化后重跑，并将证据与使命和验收标准对照。[Agent 评测](/zh-cn/software-factory/evaluation/)提供工程交付检查。平台治理还会加入访问、审计、成本和质量控制。

生命周期如下：

```text
定义 → 校验 → 发布 → 创建实例 → 执行 → 审阅 → 改进
```

更新源 Agent 包，并不能证明已有实例已经收到变更。应该测试并发布新版本，再次检查受影响的实例或工作流。

## 交付物与证据

交付物是人要审阅的东西：任务、产物、报告，或仍需批准的行动。证据是这些交付物的依据。专家工作台展示审阅发现、测试证据和安全证据。交付看板把这些记录在阶段之间传递。一句自信的结束语不能替代可复现的结果。

## 最小示例

```text
research-assistant/
├── .claude-plugin/plugin.json
├── .aiworkforce/employee.yaml
├── .aiworkforce/router.md
├── README.md
└── skills/main/SKILL.md
```

`employee.yaml` 承载岗位和使命。`router.md` 指向 `skills/main/SKILL.md`，并说明输入缺失或请求超出岗位时怎么处理。Skill 描述方法。插件文件为包命名。这些文件都不会授权仓库或外部账号。
