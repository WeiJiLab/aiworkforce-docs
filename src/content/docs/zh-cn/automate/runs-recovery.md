运行是一次 Job 执行的记录。通过运行标识、输入、会话与结果，可以判断实际发生了什么。会话执行成功与业务结果已经保存，是需要分别确认的事实。

## 检查已结束的运行

打开 Job 的运行历史，核对：

- 触发来源与输入：项目、时间范围是否符合预期？
- 执行会话：由哪个员工使用了哪些工具？
- 最终状态与输出：执行是否结束，成果是否满足任务要求？
- 已配置采集工具时的回执：Issues 是否保存到了正确目标？

采集工具是可选项。启用后，需要取得已保存事项的服务端回执，或者明确的空结果回执。仅有“已创建三个任务”的消息不足以证明保存成功。当前采集界面要求 Claude Code 执行内核。

## 重试前定位原因

| 现象           | 优先检查                           | 后续操作                           |
| -------------- | ---------------------------------- | ---------------------------------- |
| 没有出现运行   | Job 状态、规则状态、时区、事件条件 | 修正启用状态或来源配置             |
| 工具访问失败   | 员工授权与连接可用性               | 通过正常资源配置完成授权           |
| 输入不合法     | 必填字段与负载映射                 | 修正输入后发起新的手动运行         |
| 采集失败       | 保存回执或空结果回执               | 检查会话与目标，再决定是否重复执行 |
| 执行状态不确定 | 会话活动与外部副作用               | 先核对实际成果，再重新发起工作     |

执行状态不确定，可能意味着运行时已启动，但平台无法安全接续其结果。不能因为缺少最终响应，就判断工作从未发生。应检查外部系统是否已有记录、提交或消息。

## 有依据地重试

显式重试会使用已结束运行的原始输入创建新运行，并保留原记录。如果输入本身有误，应修正后发起新的手动运行。排查重复失败时，同时记录新旧两个运行 ID。

通用重试要求 Job 仍处于可触发状态，且发布版本未变。测试运行应从测试入口重新执行，工作台关联运行应从卡片恢复。不确定执行可能仍占用员工容量，需要先核对并处理，再重试。

持久化执行系统可以恢复执行记录，以及已确认可以安全重复的步骤，但不会默认认为重新调用一个不透明的 Agent 没有副作用。涉及外部写入时，应使用稳定的来源标识，并在重试前检查已有输出。

重发接受 `Idempotency-Key` 的[公开调用](/zh-cn/developer/api-reference/)时，复用同一请求的键和输入。明确要发起新执行时，再用新键。自动化页面的**手动执行一次**每次提交都会生成新键。响应丢失时，先查运行历史，再决定是否提交。请求去重只覆盖 Run 的创建。重试工作前，先检查已有的外部写入。

## 取消与交接

需要停止工作时请求取消，再检查最终状态及关联会话。取消无法撤销已完成的外部操作。

新的 Run 可以复用 Job 绑定的会话。用 Run ID 区分执行记录，在会话里阅读对话。如果采集的 Issue 进入工作台，核对所在看板的[接入规则](/zh-cn/software-factory/intake/)。
