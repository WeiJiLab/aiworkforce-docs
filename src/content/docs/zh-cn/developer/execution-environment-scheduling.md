假设会话 1、2 正在 worker A、B 上执行工具，所有者此时向会话 3 发送第一条消息。在规划的方案里，用户选择一个**执行环境**，授权平台从环境内的一组 worker 中选机。会话 3 先排队。B 完成本轮并确认进程已停止后，平台自动在 B 上启动会话 3，即使用户已经关掉浏览器。

## 两台设备今天能做到什么

普通 Claude Code 员工会话的所有者可以在首条消息前选定设备。平台负责模型循环，把工具调用发给这台设备。一次单节点 Linux ARM64 Kubernetes 试验使用了两个独立注册的 daemon、真实 WSS 连接和按脚本返回的模型响应。两个会话在各自卷的相同路径写入并读回不同标记，逐台重建空闲 Pod 后，又从原会话读回原标记。两台合计完成四个回合，收到六条成功的工具回执。另一个预先绑定 A 的会话在 A 忙、B 空闲时收到占用错误。设备注册、卷配置和手动验收步骤见[在 Kubernetes 上运行设备执行器](/zh-cn/deployment/self-host/#在-kubernetes-上运行设备执行器)。

每台 worker 有独立的设备身份、状态卷和项目卷。分配到同一台 worker 的会话能读到前一个会话留在工作目录的文件。试点因此限定为**同一所有者、同一可信项目**。会话与设备的绑定跨回合保留，每个回合只在运行和等待进程停止确认期间占用设备。会话 2 空闲时，B 可以接纳会话 3。会话 2 的下一轮仍需等 B。

## 平台需要改哪里

### 先接收消息，再选设备

在首条消息前保存用户选择的环境。现有选机入口在会话有消息后会冻结执行位置，调度器需要一个内部操作，在有空位时完成首次绑定。当前 `send_prompt` 在 WebSocket 进程中启动任务，追问队列只给单个会话的消息排序。daemon 收到的工具命令已经指定了设备，因此环境排队必须放在选机之前。

对于选择了环境的会话，平台以会话 ID 和客户端消息 ID 为唯一键，把消息和排队请求一起落库，再向用户确认接收。同一会话用同一客户端消息 ID 重试时返回原请求，该 ID 对应不同内容时拒绝。等待 worker 期间不启动模型，用户重新连接后能看到排队状态。取消或到期先于分配生效时，请求结束等待。

### 在一个事务中分配回合

调度器（dispatcher）按入队时间领取环境里最早可分配的请求，并保持同一会话内的消息有序。领取时复核所有者权限、项目和设备的环境归属。候选设备须在线、凭据有效、具备 `device_rpc` 能力且可接受新回合。已绑定的会话只等原设备。

在一个 PostgreSQL 事务中领取请求、创建或复用会话与设备及本地会话的唯一绑定、预留设备，并为该请求写入唯一的待启动回合。锁住请求，用条件更新占用设备，使两个 dispatcher 即使同时看到一个空位，也只会有一个分配成功。准入要求平台回合占用（`active_run_id`）和设备执行占用（`execution_slot_id`）都为空。

### 按原回合 ID 启动

现有 `runtime_turn` 创建回合时会拒绝同一请求再次进入。调度器需要一条按原 ID 启动已预留回合的路径。现有租约清理会把过期回合标为中断。对于尚待启动的预留，需要让接管者能接续原租约，并与清理逻辑协调。

从待启动切换到运行时校验当前调度租约版本。接管时递增版本，更新状态和派发工具命令时也校验版本，使旧 dispatcher 的操作失效。容量释放时唤醒 dispatcher。启动时和运行中定期扫描可分配请求及待启动回合，以便补上丢失的通知。

### 复用 daemon 的执行与停止证据

固定容量试点可直接复用现有 daemon。它通过出站 WSS 完成鉴权，执行发给本机的工具命令，并在 journal 中保留执行代次（generation）、结果和停止记录。当前回合结束且设备确认进程已停止后，平台可把槽位分给下一回合。

命令可能已经执行时，平台按原命令 ID 和设备执行代次核对回执与 journal。结果未知时，保留槽位隔离，并向用户显示正在等待核对。Pod 重建或调度租约到期后，要释放槽位仍需要原执行的停止证据。

## 如何验收调度器

下面是平台实现后的验收条件。准备真实 PostgreSQL、两个独立的 dispatcher 进程，以及两个分别挂载独立项目卷的 daemon。让会话 1、2 各运行一个可由测试控制结束时间的回合，分别占住 A、B。让会话 3 只执行一个工具动作，向测试文件**追加一行请求 ID**。在两块卷上分别数行，可以发现覆盖写会掩盖的重复执行。

| 操作                                                                                      | 通过条件                                                                                                          |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 两台都忙时提交会话 3，用同一消息 ID 重试，再关闭浏览器。                                  | dispatcher 扫描一轮后，数据库里只有一条会话 3 的等待记录。该请求的设备绑定、模型启动和工具命令数均为零。          |
| 保持 A 忙，让会话 2 结束并取得 B 的停止确认。让两个 dispatcher 同时尝试领取等待中的请求。 | 用户无需再发消息，会话 3 自动绑定到 B 并完成一个回合。该工具命令只有一份完成回执，B 卷有一行请求 ID，A 卷为零行。 |
| 结束 B 的回合，暂缓停止确认。                                                             | 会话 3 继续等待。停止结果未知时 B 保持隔离。                                                                      |
| 取消仍在排队的会话 3 请求，然后释放 B。                                                   | 请求保持已取消，两块卷上均没有该请求的 ID。                                                                       |
| 会话 3 在 B 上执行时，释放 A，再向会话 2 发送消息。                                       | 会话 2 等到 B 空闲后才在原工作目录启动下一回合。                                                                  |

分别在以下时刻中断负责领取的 dispatcher，由另一个进程接管，再重启原进程。每次独立重跑释放 B 的用例，用同一请求核对设备绑定、回合 ID、命令回执和两块卷上的行数。

| 中断时刻                       | 通过条件                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 分配事务提交前                 | PostgreSQL 回滚领取和预留，接管者能为原请求成功分配一次。                                                      |
| 事务已提交，启动通知发出前     | 接管者扫描到待启动记录，在原设备上启动原回合。原 dispatcher 即使迟到一步发起启动，也会因租约版本过期而被拒绝。 |
| 工具已追加标记，平台收到回执前 | 按原命令和执行代次核对。能恢复回执就归入原回合，结果未知就保持隔离。两种情况下，标记总数始终为一行。           |

## 与按会话创建沙箱的关系

Anthropic 的 Compose 快速入门通过工具结果核对实际执行容器。它的 Kubernetes Chart 使用 Agent Sandbox 控制器。dispatcher 轮询环境队列，为每个会话分配沙箱。空闲 Pod 退出后，下一条消息会让新 Pod 挂载同一块会话卷。固定 worker 方案借鉴环境排队和会话亲和性，项目卷随设备保留。[Claude Managed Agents 快速入门](https://platform.claude.com/docs/en/managed-agents/self-hosted/quickstart) · [每个会话一个沙箱](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes-per-session)

Kubernetes SIG Apps 的 Agent Sandbox 提供 `SandboxClaim` 按模板申领容量，`SandboxWarmPool` 维护预热沙箱。DeerFlow 示例把应用的获取和释放操作映射到 Claim。固定容量通过上述验收后，dispatcher 可以为新会话申领沙箱，记录 Claim 身份、发放仅限该会话的凭据，并挂载会话专属卷。会话准入、绑定和恢复仍由平台负责。[Agent Sandbox v1.0.11](https://github.com/kubernetes-sigs/agent-sandbox/tree/v1.0.11) · [预热池示例](https://github.com/kubernetes-sigs/agent-sandbox/tree/v1.0.11/examples/warmpool-quickstart) · [DeerFlow 适配示例](https://github.com/kubernetes-sigs/agent-sandbox/tree/v1.0.11/examples/deer-flow-sandbox)
