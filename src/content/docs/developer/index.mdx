## What do you want to do?

A ticket event, a button in your app, and a conversational agent can all start the same published analysis Job. Choose the guide that matches who initiates the run. If you need a tool on a particular machine or a different view of the finished report, start with that task instead.

## Example: write an analysis summary back to a new ticket

1. **Prepare the Job.** Publish and enable a Job that takes ticket content and returns a summary. Run it manually with a sample ticket to check its input fields and output. See [automation fundamentals](/automate/fundamentals/).
2. **Connect the ticket event.** Configure and enable an inbound webhook for the Job. When your backend receives a ticket creation event, send the input the Job expects. Reuse the same idempotency key if you retry that event. See the [webhook guide](/integrations/webhooks/).
3. **Associate the run with the ticket.** HTTP `202` means the platform accepted the event. Find the target Job’s `run_id` in `data.results` and store it alongside the ticket ID. If the entry has no run ID, inspect its `disposition` and `message`.
4. **Write back the summary.** Have the ticket backend poll the run’s `status`. On success, write the summary from the Job’s `output` to the original ticket. On failure, read `error` and mark the analysis as failed. See the [REST API run lookup example](/developer/api-reference/#start-and-inspect-a-run).

If you later add a “Run analysis again” button, reuse the Job and the write-back logic. On click, have the backend start a fresh run through the REST API, take the run ID from `data.id`, and look up its result.
